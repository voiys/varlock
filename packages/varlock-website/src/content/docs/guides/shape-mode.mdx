---
title: Shape mode
description: Load a schema for editors, linters, and type checkers while skipping exec(), provider lookups, and plugin downloads
---

Loading a schema normally does real work. `exec()` runs a shell command, plugin resolvers call secret stores, `@cache` opens an encrypted cache, root decorators like `@setValuesBulk` and plugin `@init*` decorators run, and a pinned plugin that isn't installed is downloaded from npm. That is what you want when running an app, but not when a tool only needs to read the schema: a type checker, a language server, or a CI lint.

Shape mode builds the graph (items, types, decorators, requiredness, sensitivity, errors) without running any of that. It is a programmatic API for tool authors. To check your own env, use [`varlock load`](/reference/cli/load-and-run/#load).

:::caution[Plugins without a manifest still run by default]
Shape mode skips `exec()`, other resolvers with side effects, and root decorator execution, and it never downloads a plugin. A plugin that ships a [manifest](#plugin-manifests) is read from it and its code never runs. A plugin that is installed or cached but has no manifest is still imported, and its module code and `process()` hooks run, unless you pass [`runPluginCode: false`](#never-running-plugin-code). See [Limits](#limits).
:::

## Using it

Pass `mode: 'shape'` when creating the graph. The graph classes are exported from `varlock` as `internal`.

```js title="check-schema.mjs"
import { internal } from 'varlock';

const { EnvGraph, DotEnvFileDataSource } = internal;

const graph = new EnvGraph({ mode: 'shape' });
await graph.setRootDataSource(new DotEnvFileDataSource('./.env.schema'));
await graph.finishLoad();

// a source that fails to parse or a missing plugin stops loading early, and items can have schema errors
const problems = [
  ...graph.sortedDataSources.flatMap((source) => source.errors),
  ...Object.values(graph.configSchema).flatMap((item) => item.errors),
].filter((e) => !e.isWarning);
if (problems.length) {
  for (const err of problems) console.error(err.message);
  process.exit(1);
}

for (const key of graph.sortedConfigKeys) {
  const info = await graph.configSchema[key].getTypeGenInfo();
  console.log(key, info.dataType?.coercedType ?? 'string', info.isRequired);
}

// everything that was not run, e.g. [{ kind: 'rootDecoratorExecute', name: 'currentEnv' }]
console.log(graph.shapeSkipped);
```

This loads the schema file and the files it imports. Value files such as `.env.local` are not picked up by a `DotEnvFileDataSource` pointed at the schema. Calling `graph.resolveEnvValues()` also works in this mode. It only runs the [pure resolvers](#pure-resolvers) listed below.

## What changes

| | Default mode | Shape mode |
|---|---|---|
| Resolver functions | all run | only [pure](#pure-resolvers) ones run, the rest resolve to `undefined` |
| Root decorators | `execute()` runs | `execute()` is skipped, so values set by `@setValuesBulk` and items it creates with `createMissing=true` are not in the graph. Items referenced in their arguments (`$VAR`) are still resolved and validated |
| Cache | `@cache` opens a store | no cache store is created |
| Plugins | a pinned plugin is downloaded if missing, and its code runs | never downloaded. If it isn't installed or cached, loading reports a schema error. A plugin that ships a [manifest](#plugin-manifests) is read from it instead of running its code |
| `process.env` | overrides item values, and builtin variables read it | ignored. Values come from the files that were loaded, and builtin variables only see an env you pass in explicitly (`graph.processEnvOverride`) |
| Code generation | writes wherever `path` points | only inside the directory of the root schema or directory; a path that leaves it (`..`, absolute, or through a symlink) is a schema error |
| Files | read as usual | a schema or env file that is not a regular file (a named pipe or a device), whether it is the root file, imported directly, or found in an imported directory, is a loading error instead of a read that never returns |
| Regexes in the schema | run on a linear-time engine (RE2). A pattern it does not support runs on the JavaScript engine, with a warning | run on a linear-time engine (RE2). A pattern it does not support is not run: the match is unknown, with a warning. See [Regexes](#regexes) |

Everything skipped is recorded in `graph.shapeSkipped` as `{ kind, name, itemKey? }`, where `kind` is `resolver`, `rootDecoratorExecute`, `cacheStore`, `pluginDownload`, `codegenWrite`, `coerce` (see [Plugin manifests](#plugin-manifests)), `pluginCode` (see [Never running plugin code](#never-running-plugin-code)), or `regex` (see [Regexes](#regexes)), and `itemKey` is the item whose value was being resolved when a resolver or coercion was skipped. Tools can use it to tell users which values could not be computed.

Apart from those differences, a tool sees the same types that [code generation](/guides/code-generation/) produces, and the same requiredness, sensitivity, and validation messages, except where a decorator or function depends on a value that was skipped (see [Pure resolvers](#pure-resolvers)), and except for the checks a plugin read from its [manifest](#plugin-manifests) does in code (its `process()` hooks and data type `validate()`), which don't run and are not listed in `shapeSkipped`. [Builtin variables](/reference/builtin-variables/) such as `VARLOCK_ENV` are computed from an env you pass in explicitly, or from an empty one, so the same schema gives the same result on any machine. Without CI variables in that env, `VARLOCK_BRANCH` is unknown (and listed in `shapeSkipped`), because the local `git branch --show-current` lookup is skipped.

### Pure resolvers

These built-in resolvers only read other values, so they still run: `concat()`, `fallback()`, `ref()`, `regex()`, `remap()`, `forEnv()`, `eq()`, `if()`, `ifs()`, `not()`, `and()`, `or()`, `isEmpty()`, `domainFromUrl()`, and `inferFromPrefix()`. That is enough to evaluate `@currentEnv`, `@required=forEnv(production)`, and `${REF}` expansion.

Everything else resolves to `undefined`: [`exec()`](/reference/functions/#exec), the random generators, [`generateOtp()`](/reference/functions/#generateotp), [`cache()`](/reference/functions/#cache), and plugin resolvers that are not [marked pure](#marking-plugin-resolvers-as-pure). An item whose value depends on one of them (directly, or through a reference like `COPY=$TOKEN`) is unknown. It is left unset and is not coerced, validated, or reported as a missing required value. A `@disable` or `@import(..., enabled=...)` condition that depends on one is treated as enabled, so the file's items stay in the graph. An error that a resolver raises because one of its own inputs is unknown (for example `domainFromUrl()` of a half-built URL) is cleared for an item's value. An error from a part of the expression that doesn't depend on a skipped resolver is still reported, so `concat(exec(...), domainFromUrl("mailto:x"))` still shows the `domainFromUrl()` error. It is not cleared inside a `@disable` or `@import` condition.

A function or decorator that depends on a skipped value, such as `if()`, `eq()`, or `@sensitive=eq(exec("..."), yes)`, sees it as empty, so what it returns can differ from default mode. If `@currentEnv` itself points at a skipped value, `forEnv()` has no environment to compare against and reports an error.

## Limits

Shape mode does not sandbox plugin code. By default, a plugin that is installed or cached and does not ship a [manifest](#plugin-manifests) is still loaded, so its module code runs when it is imported, and its data types, decorators, and the `process()` hooks of its resolvers are registered and run as usual. If a tool opens schemas you don't trust, for example from a repository you just cloned, it should pass [`runPluginCode: false`](#never-running-plugin-code), or only open them where the plugins it finds are acceptable to run, or inside a sandbox. `plugin.loadedFromManifest` on each entry of `graph.plugins` tells a tool whether that plugin's code ran. A plugin that is missing is never fetched or run.

`pure` on a plugin resolver is a promise made by code that already runs, so shape mode trusts it the same way. A plugin manifest that lets tools skip importing plugin code would not carry that flag.

Default mode still runs a schema regex that the linear-time engine does not support (lookahead, lookbehind, backreferences) on the JavaScript engine, which has no timeout, so such a pattern with catastrophic backtracking can stall `varlock load` on a schema you don't trust. Shape mode never does (see [Regexes](#regexes)).

### Never running plugin code

Pass `runPluginCode: false` to make sure no plugin code runs:

```js
const graph = new EnvGraph({ mode: 'shape', runPluginCode: false });
```

A plugin that ships a [manifest](#plugin-manifests) is still read from it. A plugin without one is not loaded at all:

- its `@plugin` line gets a warning saying it was not loaded, and `shapeSkipped` gets `{ kind: 'pluginCode', name }`
- a decorator or data type that no loaded plugin registers is a warning instead of an error, because it may come from that plugin. The decorator is ignored
- an item whose `@type` is such a data type is a `string` in generated types, its value is unknown (listed as `coerce`), and it is treated as sensitive, since the plugin might mark it so
- a function that nothing registers resolves to an unknown value (listed as `resolver`), and its item is treated as sensitive
- the plugin's `@init*` decorators, standard vars, code generators, and icons are missing

While every plugin loaded, an unknown decorator, data type, or function is still an error. `runPluginCode: false` is only allowed with `mode: 'shape'`, and the default is `true`, so a plugin without a manifest keeps working in tools until it ships one.

### Regexes

In both modes, every regex that comes from the schema runs on [RE2JS](https://github.com/le0pard/re2js), a linear-time engine: `regex()`, the `matches` option of `string`, `url` and `domain` (as `regex()`, `/pattern/flags` or a plain string), the patterns `remap()` compares against, and `@auditExtraPatterns()`. A pattern with catastrophic backtracking such as `^(a+)+$` returns in microseconds instead of blocking the thread.

The pattern is translated so a match means the same thing as in JavaScript (`\s`, `.` and `\uXXXX` are rewritten). Some patterns can't be evaluated exactly on RE2: backreferences, lookahead and lookbehind, inline modifiers, an empty class (`[]`, `[^]`), `^` or `$` with the `m` flag, and the `v` flag. Such a pattern gets a warning. Default mode runs it on the JavaScript engine for now, so it validates as before (this fallback will be removed in a future version). Shape mode does not run it: the match is unknown. The same goes for an input with characters outside the Basic Multilingual Plane (emoji, for example) against a pattern without the `u` flag, without the warning. An unknown match is listed in `shapeSkipped` as `{ kind: 'regex', name }`, a `matches` check with it reports no error (the warning says whether the value matches is unknown), and `remap()` resolves to an unknown value. Case-insensitive matching of a few non-ASCII letters (such as `ſ` and the Kelvin sign) can differ from JavaScript.

Key globs in `pick`, `omit` and `@auditIgnoreKeys` are matched in linear time in both modes.

## Marking plugin resolvers as pure

Plugin authors can opt a resolver into shape mode with `pure: true`. Set it only when the resolver reads nothing but its arguments and other items: no shell, network, filesystem, secret store, or randomness.

```ts title="my-plugin.ts"
import { plugin } from 'varlock/plugin-lib';

plugin.registerResolverFunction({
  name: 'upper',
  pure: true,
  argsSchema: { type: 'array', arrayExactLength: 1 },
  async resolve() {
    return String(await this.arrArgs[0].resolve()).toUpperCase();
  },
});
```

If you leave `pure` out, the resolver is skipped in shape mode, which is the safe default for anything that talks to a provider. Older varlock versions ignore the flag.

## Plugin manifests

A plugin manifest is a JSON file, shipped in the plugin package, that describes what the plugin registers: its root and item decorators, data types, resolver functions, code generators, icon, bundled icons, and standard vars. In shape mode, varlock reads it instead of importing the plugin, so the graph gets the plugin's decorators, data types, and resolvers without running any plugin code. Default mode ignores it and runs the plugin as usual.

Item types, sensitivity, and requiredness come out the same as when the plugin runs, except where they depend on the plugin code listed below. That includes a decorator such as `@required=eq($PORT, 8080)` that reads a value which is unknown without that code (see [Pure resolvers](#pure-resolvers)).

The 1Password plugin ships one. Other first-party plugins will follow.

A manifest only holds data. Nothing a plugin does in code is carried, so with a manifest, shape mode does not run:

- the plugin's `process()` hooks, so checks such as a duplicate `@initOp` id or an `op()` call naming an unknown instance are not reported, and anything a hook sets (for example a resolver's inferred type set in `process()` rather than on its definition) is missing
- data type `validate()`, so a check such as "token must start with `ops_`" is not reported
- data type `coerce()`. The value of an item whose type the plugin coerces in code (directly, or as the element of a type such as `array(myType)`) is unknown, like a value from a skipped resolver, and is listed in `graph.shapeSkipped` with `kind: 'coerce'`
- any resolver, including one marked `pure: true`, so its items are unknown and listed in `graph.shapeSkipped`

A data type that takes settings, like `myType(max=10)`, is described as it is with no settings, so settings that change its coerced type, sensitivity, or other metadata are not reflected.

### Shipping a manifest

Point a `./manifest` export in the plugin's `package.json` at the file, and include it in the published files:

```json title="package.json"
{
  "exports": {
    "./plugin": "./dist/plugin.cjs",
    "./manifest": "./plugin-manifest.json"
  },
  "files": ["dist", "plugin-manifest.json"]
}
```

Generate the file from the built plugin rather than writing it by hand. `generatePluginManifest()` runs the plugin, so only use it on your own plugin:

```js title="scripts/generate-manifest.mjs"
import fs from 'node:fs';
import { internal } from 'varlock';

// manifestPath is where the package's "./manifest" export points
const { manifest, manifestPath } = await internal.generatePluginManifest('.');
fs.writeFileSync(manifestPath, `${JSON.stringify(manifest, null, 2)}\n`);
```

Run it after each build, or check it in CI, so the manifest never falls behind the plugin. The varlock repo does this for its own plugins with `bun run plugin-manifests` and `bun run plugin-manifests --check`.

Varlock reads the manifest only when its `name` matches the package name, and the `./manifest` path must stay inside the package. A manifest that is missing, unreadable, or invalid is a schema error on the `@plugin` line, and the plugin does not run. A plugin that registers credential proxy transform schemes can't be described by a manifest yet, and `generatePluginManifest()` reports an error for it.
